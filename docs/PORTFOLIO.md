# 지원·면접 설명 초안

지원서에 사용할 사실과 설명을 정리한 초안이다. 실제 상용 Android 운영 경험이나 특정 업체 내부 구조를 경험한 것처럼 표현하지 않는다. 수치는 [고정 M2 검증](evidence/M2_REVIEW.md)을 기준으로 하며 이후 변경은 해당 실행 근거를 함께 제시한다.

## 프로젝트 소개

Local Link Lab은 Android 단말과 PC POS 시뮬레이터 사이에서 연결 단절·응답 유실·앱 프로세스 종료를 재현하고, 접수한 주문의 보존과 중복 저장 방지를 확인하는 Kotlin/Compose·Room·TCP·SQLite 프로젝트다. 연결 실패 뒤 업무를 계속할 수 있는 동작과 그 동작을 자동으로 검사하는 체계를 함께 만들었다.

핵심 사례는 POS가 주문을 저장했지만 응답이 사라지는 상황이다. 앱은 기존 ID로 재시도하고 POS는 같은 주문의 최초 영수증을 돌려준다. 접수 전에 만든 기준과 Android/서버의 전체 행을 대조해 누락·추가 주문·잘못된 완료를 확인한다. 자동 검사 자체가 오류를 찾는지도 의도적 결함 사본 두 개로 확인했다.

## 주문이 확인되는 경로

```mermaid
flowchart LR
    UI[접수 초안 ID] -->|원자적 저장| L[Room PENDING]
    L --> W[전경 Controller]
    W -->|같은 ID와 본문| P[POS 주문·영수증 commit]
    P -->|ACK 최초 영수증| A[Room ACK commit]
    A --> V[화면에 POS 저장 확인]
    W -. 연결 실패 시 보존·재시도 .-> L
```

ACK가 유실되면 기존 PENDING을 유지하고 같은 ID로 다시 보낸다. POS는 최초 영수증을 반환하고 추가 주문 행을 만들지 않는다.

## 설명할 설계 판단

| 판단 | 선택과 이유 | 실행 근거 |
|---|---|---|
| 보관 용량 초과 | 이미 접수한 주문을 지우지 않고 새 접수를 거부 | Room 한도/전체 기존 ID 보존 검사 |
| 응답 없음 | 주문 실패를 확정하지 않고 동일 ID·본문으로 재시도 | S02 최초 ACK 유실, 최초 영수증 유지 |
| 목적지 교체 | 주소와 DB 정체성을 분리하고 제출 트랜잭션에서도 ID 확인 | C07 다른 DB 제출·저장 0건 |
| 앱 수명 | Application의 단일 전송 소유자와 영속 업무 상태 분리 | 실제 PID 종료·명시적 재실행 관측 |
| 진단 실패 | 연결 확인 오류를 표시하면서 기존 설정의 전송을 복원 | OPUS 반례 → M1 수정 → JVM/Android 회귀 |
| 검사의 신뢰성 | 정상 통과에 더해 데이터 오류를 일으킨 사본도 검출 | MUT01 추가 주문, MUT02 POS 없는 완료 |

## 지원서 문장 예시

> Android 단말–POS 시뮬레이터의 주문 보존·복구 실험을 구현했습니다. Room 접수 commit, 요청 ID 기반 POS 중복 방지, 제한된 재시도와 프로세스 재실행 복원을 연결하고 API 29 에뮬레이터에서 장애·복구 6개를 검증했습니다. ID 재발급 및 ACK 전 완료 결함 사본을 같은 판정기로 검출했으며, 독립 검토에서 발견한 연결 진단 후 전송 중단 문제를 재현·수정하고 회귀 테스트로 고정했습니다.

본인의 실제 경력과 연결할 때는 기존 현장 경험에서 무엇을 배웠고 Android에서는 어떤 판단을 새로 확인했는지 구분한다. 개인 저장소의 숫자·장비 수·상용 운영 성과는 별도 근거를 확인한 뒤 사용한다.

## AI 협업을 설명하는 방식

구현·검증 보조에 Codex를, 고정 코드의 독립 검토에 OPUS를 사용했다. 채택 기준은 모델 간 동의가 아니라 재현 결과와 저장 계약이다. OPUS의 DB 교체 테스트는 수정 후 새 DB ID를 사용한 주문이 성공해야 한다는 계약에 맞춰 보완했고, 원본과 변경 이유를 모두 남겼다. 사용자는 아래 질문의 답을 코드와 관측으로 직접 설명할 수 있도록 확인한다. AI가 작성한 코드를 모두 스스로 작성했다고 설명하지 않는다.

## 코드 없이 먼저 설명해 볼 질문

1. **요청 ID는 왜 저장해야 하나?** 초안 ID·불변 본문·대상 DB가 함께 commit돼야 재실행·재시도에서 같은 업무를 식별한다. ID를 먼저 메모리에서 생성하는 것은 가능하지만 저장 확정 전에 전송하면 안 된다.
2. **저장 중 앱이 죽으면?** SQLite 트랜잭션이 미완료라면 원자적 복구 대상이며, commit된 행은 UI가 갱신되지 않았어도 재조회한다. 프로세스 종료 검증을 물리 전원 차단 보장으로 확대하지 않는다.
3. **TCP 연결을 왜 바로 알 수 없나?** 케이블 분리나 침묵 상대는 즉각 EOF를 보내지 않는다. 요청 전체의 제한 시간으로 종료하고 소켓을 실제 닫는다. 부분 응답이 시간을 계속 연장하지 못하게 한다.
4. **timeout과 코루틴 취소가 어떻게 다른가?** 한 통신 시도의 자체 deadline은 재시도 가능한 통신 오류다. 전경 이탈 등 상위 job 취소는 전파하며 새 전송을 시작하지 않는다.
5. **Compose 회전과 프로세스 종료를 어떻게 구분하나?** 화면 초안은 rememberSaveable로 유지하고 commit된 업무는 Room에서 읽는다. 전송 소유자는 화면 인스턴스가 아니라 Application에 둔다. rememberSaveable이 주문 DB를 대신하지 않는다.
6. **중복 방지는 어디까지인가?** 같은 POS DB 이력에서 동일 ID/본문의 주문 저장 효과와 최초 영수증을 보존한다. DB 삭제·옛 백업 복원·복제 분기·외부 실결제·프린터까지 exactly-once를 주장하지 않는다.
7. **연결 확인 실패가 왜 전송을 멈췄나?** collectLatest가 기존 worker를 취소한 뒤 probe 오류로 새 실행 전체가 끝났다. 오류 진단과 영속 설정 기반 전송 복귀를 분리하고 사용자 중지 플래그를 유지했다.
8. **테스트가 초록이면 충분한가?** 실행 누락, 잘못된 기대값, 느슨한 판정으로도 초록이 될 수 있다. 기준값·전체 행·영수증 대조와 의도적 결함 검출, Python 최적화 실행의 검사 유지까지 확인했다.

자동 검색·BLE·USB·다중 단말·배포 롤백은 후속 과제다. 실기기를 확보하면 API·LAN·서명/설치·제조사 정책을 별도 검증한다. 지원 준비에서는 기능 수보다 이 경계와 선택 이유를 설명하는 데 우선순위를 둔다.
