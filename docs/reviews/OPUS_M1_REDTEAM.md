Codex가 구현·통합·수정·실행 근거 관리를 맡는다. OPUS는 위 고정 커밋을 독립적으로 검토한다. 이 문서는 업무 요청이며 OPUS 검토나 실행 완료 기록이 아니다. 검토 중 브랜치 최신 상태가 바뀌어도 기준 SHA를 바꾸지 않는다.

목표는 주문 유실·중복 처리·잘못된 완료 표시·복구 정지를 일으킬 수 있는 최소 반례를 찾는 것이다. 실제 결제나 외부 서비스는 대상으로 삼지 않는다. 합성 주문과 격리한 임시 DB를 사용한다.

## 우선 검토할 다섯 경계

1. **접수와 완료의 경계**: 로컬 commit 전후, POS commit 후 ACK 유실, ACK 수신 후 로컬 commit 실패에서 ID·본문·상태가 보존되는가? 화면이 저장 사실보다 먼저 완료를 표시할 수 있는가?
2. **수명과 사용자 조작**: 전경/백그라운드, 회전, 일시 중지/재개, 연결 확인, 새 주문 접수가 겹칠 때 worker가 둘이 되거나 깨우기 신호를 놓치거나 사용자 중지가 풀리는가? 취소가 일반 재시도로 바뀌는가?
3. **목적지와 중복 방지**: 같은 DB의 IP 변경, 다른 DB 연결, hello 직후 DB 교체, 동시 중복, 같은 ID의 다른 본문에서 원래 주문과 최초 영수증이 보존되는가?
4. **통신과 자원 종료**: 침묵·부분 수신·잘못된 응답에서 전체 제한 시간과 소켓 종료가 실제로 적용되는가? 요청 ID가 다른 ACK나 잘못된 프레임이 업무 상태를 바꿀 수 있는가?
5. **검사의 신뢰성**: 정상 테스트가 위반 구현도 통과시키는가? 기준 주문과 POS 전체 행을 비교해 추가 고아 주문까지 찾는가? 실행 누락·skip·환경 실패를 성공이나 결함 검출로 잘못 세는가?

각 항목은 조사 질문이며 이미 존재한다고 단정한 버그 목록이 아니다. M1 요청서의 알려진 M2 보강 항목을 새로운 발견처럼 중복 보고하지 말고, 예상보다 영향이 크다면 근거를 추가한다.

## 맡길 수 있는 코딩 작업

발견한 문제의 **최소 재현 테스트 또는 독립 실행 스크립트**를 작성해 결과에 첨부한다. 제품 코드 수정과 저장소 push/merge는 Codex가 담당한다. 재현 코드는 임시 checkout에서 작성하거나 적용 가능한 diff로 전달한다. Android 실행 환경이 없으면 JVM/Python에서 확인한 부분과 Android에서 확인해야 할 부분을 나눈다.

테스트를 실행할 수 있으면 명령·환경·기준 SHA·실패 메시지를 남긴다. 실행하지 못하면 `NOT_RUN`과 이유를 적는다. 컴파일 실패나 환경 오류는 제품 결함을 재현한 증거가 아니다. 제안한 테스트가 기존 구현에서 통과한다면 실패 재현으로 표시하지 않는다.

## 결과 형식

- 먼저 가장 영향이 큰 발견을 요약한다. 스타일·취향·불필요한 기능 확장은 후순위로 둔다.
- 각 발견: `번호 / 우선순위 / 파일·줄 / 트리거 순서 / 기대와 실제 / 깨지는 불변식 / 실행 여부 / 최소 재현 / 권고`.
- 확인된 결함, 정적으로 발견한 위험, 추가 검증이 필요한 가설을 구분한다.
- 마지막에 `M1 승인 / 조건부 승인 / 수정 후 재검토` 중 하나와 반드시 먼저 고칠 항목을 적는다. 전체 v0.1 완료를 승인하는 검토로 확장하지 않는다.
- 사용자에게 보낼 면접 질문은 핵심 설계 판단 3개 정도만 덧붙인다.

Codex는 보고된 재현을 확인하고 회귀 테스트·수정에 반영한다. 의견이 다르면 실행 결과와 계약을 근거로 처리 이유를 남긴다. 다음 묶음 검토는 M2 장애 검증 완료 시점이다.
