# M0 설계 검토 요청

검토자: OPUS. 이번 요청은 구현 전 계약 검토다. 새로운 기능 제안은 후속 목록으로 분리하고 v0.1 완료를 막는 결함을 우선한다.

## 입력

- 전달한 Git 커밋 또는 검토 ZIP의 `REVISION.txt`를 기준으로 읽는다.
- 읽는 순서: `docs/SCOPE.md`, `docs/PROTOCOL.md`, `docs/SCENARIOS.md`, `spec/scenarios.json`, `docs/DECISIONS.md`.
- `README.md`와 `docs/CONTROL.md`에서 실제 구현·실행 상태를 확인한다.
- 아직 APK·SDK·POS 구현은 없다. 명세 검사 성공을 제품 테스트 성공으로 해석하지 않는다.

## 검토할 항목

1. UUID 생성 시점과 주문·ID의 원자적 저장, 전송·UI 표시 순서가 정확한가?
2. POS 고유 제약과 단일 트랜잭션, 동시 중복, 같은 ID·다른 본문, receipt 재사용에 빈틈이 있는가?
3. 요청별 TCP 연결과 전체 제한 시간이 응답 침묵·blocking I/O 취소를 처리할 수 있는가?
4. FIFO의 앞 주문 정체, 재시도 상한, 일시 중지, 목적지 변경 제한이 서로 모순되지 않는가?
5. 주문 취소 제외와 DB 존속 기간의 중복 방지 경계가 명확한가?
6. PC 대역·TCP·Android 증거 구분, am kill/force-stop 구분, 결함 사본의 검출 판정이 타당한가?
7. Windows + 삼성 구형폰의 첫 왕복을 막을 누락이 있는가? 현재 범위에서 필수인가?

## 반환 형식

각 지적: `ID | 중요도(P1/P2/P3) | 파일·절 | 실패 상황 | 근거·재현 | 최소 수정안`.

끝에 `M1 진행 가능 / 수정 후 가능`을 쓰고, 필수 수정과 후속 제안을 나눈다. 실행하지 않은 코드는 실행했다고 쓰지 않는다. 의견만으로 합의를 만들기보다 명세상 반례를 제시한다.

## 반영할 기존 의견

OPUS의 저장 원자성·POS 중복 방지·제한 시간·취소 범위·보장 기간·순서·Windows 네트워크·종료 방식·검토 횟수·공개 출처 제안을 반영했다. ID 생성 자체를 트랜잭션 안으로 제한하는 대신, 저장 확정과 전송 순서를 요구한다. v1은 요청마다 TCP를 열어 heartbeat를 제외했다. 이 두 판단을 특히 검토해 달라.
