# M2 독립 검토 준비본 — M1 수정 통합 재검증 중

이전 검증 구현은 `70a4ecaa31fb8fa0f0b1026da390ccf15726c98c`다. M1 검토 수정본을 현재 통합했으며, 아래 요청은 새 CI 결과를 고정한 뒤 갱신한다. 지금은 이전 SHA로 새 수정본을 검토하지 않는다. [M2 실행 근거](../evidence/M2.md)에 실제 결과와 미검증 범위를 기록했다. 후속 커밋은 이 보고와 요청 문서만 추가한다. M1에 대한 OPUS 검토 결과를 먼저 반영하고, 검토할 코드가 달라지면 기준 SHA와 결과를 다시 고정한다. 이 문서는 OPUS 검토 완료 기록이 아니다.

## 검토 목적

장애 시나리오가 실제 앱과 OS에서 실행됐는지, 판정기가 주문 유실·중복·잘못된 완료를 놓치지 않는지, 의도적 결함을 실제 데이터 위반으로 잡았는지 독립적으로 확인한다.

1. `lab/android_run.py`: commit 사건 이후에 장애가 주입되는가? PID 종료·재실행을 실제로 관측하는가? 실패나 실행 누락이 PASS가 될 경로가 있는가?
2. `lab/verdict.py`: 앱과 POS가 동시에 잘못된 ID로 바뀌어도 접수 전 기준으로 검출하는가? 추가 고아 주문·본문·영수증을 대조하는가?
3. `lab/mutations.py`: 정상과 동일한 판정기를 쓰는가? 빌드/설치/환경 실패를 결함 검출로 오인하는가? 결함 diff가 주장한 고장과 일치하는가?
4. `app/src/debug`: 제어 코드의 권한, 결과 파일, 예외·제한 시간, release 제외가 올바른가? 실제 화면의 Controller와 다른 경로로 보존 보장을 우회하는가?
5. `DestinationVerifier.kt`와 `LinkApplication.kt`: 재개 전 확인, 취소, 사용자 중지, 확인 실패 시 보존이 계약과 일치하는가? hello와 실제 주문 사이 DB 교체도 차단되는가?

발견은 번호·우선순위·파일/줄·재현·기대와 실제·실행 여부·권고를 포함한다. 확인한 버그와 추가 검증이 필요한 가설을 구분한다. 변경 범위를 확대하는 제안보다 데이터 보존 및 증거의 신뢰성을 우선한다.

면접 설명 후보는 세 가지다: 왜 중복 방지 ID를 재시도마다 바꾸면 안 되는지, force-stop 후 자동 재실행을 보장하지 않는 이유, 정상 테스트 통과와 결함 검출 확인이 각각 무엇을 증명하는지.
