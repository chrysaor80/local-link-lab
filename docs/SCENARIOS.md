# 시나리오와 검증 증거

정본은 [scenarios.json](../spec/scenarios.json)이다. 아래는 사람이 읽는 대응표다. 현재 전부 계획이며 제품 테스트 실행 결과가 아니다.

| ID | 검증 대상 | 재현 지점과 기대 결과 |
|---|---|---|
| S00 | 정상 왕복 | 로컬 commit → 전송 → POS commit → ACK → 로컬 확인. POS 1건 |
| S01 | 연결 단절 | 로컬 commit 이후 첫 전송을 차단하고 복구. ID·본문 보존, POS 1건 |
| S02 | 처리 후 응답 유실 | POS commit 이벤트 직후 ACK를 버리고 닫기. 재시도 ACK의 receipt_id 동일, POS 1건 |
| S03 | Android 프로세스 종료 | 로컬 commit 확인 후 미확인 상태에서 종료·명시적 재실행. 같은 ID·본문 복원 |
| S04 | 응답 없는 상대 | 요청을 읽은 서버가 응답도 연결 종료도 하지 않음. 시도 전체 제한 시간에 종료, 상한 후 일시 중지 |
| C01 | 저장·용량 실패 | 한도 경계 및 트랜잭션 실패. 접수 완료 표시·전송 없음, 기존 주문 보존 |
| C02 | 동시 중복·ID 충돌 | 독립 연결로 같은 요청을 동시에 전송, 이후 같은 ID의 다른 본문. 1건·같은 receipt, 충돌은 거부 |
| C03 | ACK 경계와 순서 | ACK 전 완료 금지, ACK 후 로컬 기록 실패 시 재전송, 뒤 주문 대기 |
| C04 | 전송 취소 | 재시도 대기/읽기 중 worker 취소. 소켓과 작업 종료, 주문 보존, 새 worker는 하나 |
| C05 | 메시지 경계 | 분할 read, UTF-8·길이·타입 오류, 다른 ID 응답. 정당한 프레임만 처리 |

## 실행 수준

- **JVM_UNIT**: 실제 Kotlin 핵심 코드 + 가짜 전송/저장소. 코루틴 시간·난수 통제. Android OS·Room·실제 TCP 검증이라고 쓰지 않는다.
- **POS_INTEGRATION**: 실제 POS 코드·임시 SQLite 파일·실제 loopback TCP. 별도 DB connection으로 저장 결과를 읽는다.
- **ANDROID_MANUAL**: Windows + 기기 또는 에뮬레이터에서 실제 앱 실행. 두 환경을 결과에 명시한다.
- 여러 OS를 자동 실행하거나 무선 간섭을 재현하는 것은 후속 범위다. S04는 응답 침묵을 재현하며 랜선 제거와 동일한 물리 현상을 검증했다고 쓰지 않는다.

## 사건 기준 장애 주입

`LOCAL_COMMITTED`, `POS_COMMITTED`, `ACK_RECEIVED`, `LOCAL_ACK_COMMITTED`를 요청 ID와 함께 관측한다. S02는 시뮬레이터의 POS commit 직후 hook에서 ACK를 한 번 버린다. 임의 sleep으로 저장 시점을 추측하지 않는다. 실패 실행도 DB와 이벤트 순서를 남긴다.

앱·POS 로그만으로 판정하지 않는다. 접수한 ID·본문 집합과 실제 POS 행·receipt_id, 로컬 상태를 대조한다. 개수만 같고 주문이 바뀐 경우를 통과시키지 않는다.

## 프로세스 종료 구분

S03은 `am kill`과 `am force-stop`을 별도 실행으로 기록한다. `am kill`은 앱을 백그라운드로 보낸 뒤 실행하고 실제 PID 종료를 확인한다. 종료되지 않았다면 해당 검증은 BLOCKED다. `force-stop`도 명시적 재실행 후 복원을 확인하며 OS 메모리 회수와 동일하다고 표기하지 않는다. 두 경우 모두 실행 중이던 작업이 자동으로 살아난다고 기대하지 않는다.

DB close/open은 저장소 재개 테스트다. 프로세스 종료 증거가 아니다. 자세한 절차는 [Windows 실행 준비](WINDOWS.md)에 있다.

## 테스트 자체 검증

- **MUT01:** 재시도 시 새 ID를 발급하도록 만든 사본 → S02가 POS의 중복 주문을 검출해야 한다.
- **MUT02:** ACK 전에 로컬 완료를 기록하는 사본 → S01/C03이 누락을 검출해야 한다.
- 정상 기준 커밋이 먼저 통과해야 한다. 결함 사본이 컴파일 실패·환경 장애로 실패한 것은 검출 성공이 아니다. 기대한 데이터 불변식 위반을 확인한다.
- 테스트가 결함의 존재를 직접 검사하거나 결함 모드 자체를 실패 이유로 삼지 않는다. 같은 결과 판정 코드를 쓴다. 결함 스위치는 배포 APK에 넣지 않는다.

## 결과 형식과 배포 조건

각 실행은 source_commit, scenario_id, execution_level, OS/기기, 시작·종료 시각, 실제 실행 명령, 주입 사건, 관측 결과, 판정, 로그/DB 증거 위치를 남긴다.

판정은 PASS / FAIL / BLOCKED / NOT_RUN. 종료 코드 0만으로 전체 통과를 결정하지 않는다. 필수 관측이나 필수 실행이 없으면 전체 성공이 될 수 없다. 재실행 통과가 이전 실패를 지우지 않는다.

M3의 CI는 명세 검사·핵심 JVM 테스트·POS 테스트에 의존하는 APK 작업으로 구성한다. 필수 job의 실패·취소·skip은 배포 후보 생성 조건을 만족하지 못한다. 실제 GitHub Actions 실행을 확인하기 전에는 CI가 검증됐다고 쓰지 않는다. 실기기 결과는 별도 증거이고 CI 통과가 대신하지 않는다.
