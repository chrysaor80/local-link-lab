# 시나리오와 검증 증거

정본은 [scenarios.json](../spec/scenarios.json)이다. 아래는 사람이 읽는 대응표다. 이 표는 요구하는 검증의 정의다. 실제 실행 결과는 CONTROL과 evidence에 별도로 기록한다.

| ID | 검증 대상 | 재현 지점과 기대 결과 |
|---|---|---|
| S00 | 정상 왕복 | 로컬 commit → 전송 → POS commit → ACK → 로컬 확인. POS 1건 |
| S01 | 연결 단절 | 로컬 commit 이후 첫 전송을 차단하고 복구. ID·본문 보존, POS 1건 |
| S02 | 처리 후 응답 유실 | POS commit 이벤트 직후 ACK를 버리고 닫기. 재시도 ACK의 receipt_id 동일, POS 1건 |
| S03 | Android 프로세스 종료 | 로컬 commit 확인 후 미확인 상태에서 종료·명시적 재실행. 같은 ID·본문 복원 |
| S04 | 응답 없는 상대 | 요청을 읽은 서버가 응답도 연결 종료도 하지 않음. 시도 전체 제한 시간에 종료, 상한 후 일시 중지 |
| C01 | 저장·용량 실패 | 한도 경계 및 트랜잭션 실패. 접수 완료 표시·전송 없음, 기존 주문 보존 |
| C02 | 동시 중복·ID 충돌 | 독립 연결로 같은 요청을 동시에 전송, 이후 같은 ID의 다른 본문. 1건·같은 receipt, 충돌은 거부 |
| C03 | ACK 경계와 순서 | ACK 전 완료 금지, ACK 후 로컬 기록 실패 시 재전송, NEEDS_ATTENTION은 보존하고 다음 PENDING 진행 |
| C04 | 전송 취소 | 재시도 대기/읽기 중 worker 취소. 소켓과 작업 종료, 주문 보존, 새 worker는 하나 |
| C05 | 메시지 경계 | 분할 read, UTF-8·길이·타입 오류, 다른 ID 응답. 정당한 프레임만 처리 |
| C06 | 침묵 클라이언트 | POS에 연결 후 완전한 프레임을 보내지 않음. 다른 요청 정상 처리, 전체 수신 제한 뒤 연결 해제 |
| C07 | 주소 변경 | 미확인 주문이 있어도 같은 DB의 새 주소 허용. 다른 DB·hello 이후 DB 교체는 주문 쓰기 없이 거부 |

## 실행 수준

- **JVM_UNIT**: 실제 Kotlin 핵심 코드 + 가짜 전송/저장소. 코루틴 시간·난수 통제. Android OS·Room·실제 TCP 검증이라고 쓰지 않는다.
- **POS_INTEGRATION**: 실제 POS 코드·임시 SQLite 파일·실제 loopback TCP. 별도 DB connection으로 저장 결과를 읽는다.
- **ANDROID_EXTERNAL**: 실제 앱과 Room을 외부 Python/adb 실행기가 제어하고 실제 TCP/POS와 비교한다. PID 종료와 명시적 재실행을 직접 관측한다. 자동 데이터 초기화는 폐기 가능한 에뮬레이터에 제한한다.
- **ANDROID_MANUAL**: Windows + 기기 또는 에뮬레이터에서 실제 앱 실행. 두 환경을 결과에 명시한다.
- 여러 OS를 자동 실행하거나 무선 간섭을 재현하는 것은 후속 범위다. S04는 응답 침묵을 재현하며 랜선 제거와 동일한 물리 현상을 검증했다고 쓰지 않는다.

## 사건 기준 장애 주입

`LOCAL_COMMITTED`, `POS_COMMITTED`, `ACK_RECEIVED`, `LOCAL_ACK_COMMITTED`를 요청 ID와 함께 관측한다. S02는 시뮬레이터의 POS commit 직후 hook에서 ACK를 한 번 버린다. 임의 sleep으로 저장 시점을 추측하지 않는다. 실패 실행도 DB와 이벤트 순서를 남긴다.

앱·POS 로그만으로 판정하지 않는다. 시나리오마다 새 POS DB와 별도의 불변 접수 기준 집합을 만든다. 앱 DB의 ID를 나중에 바꾸어도 기준 집합은 바뀌지 않는다. 복구 완료 후 POS 전체 행의 (request_id, 본문) 집합이 기준 집합과 양방향으로 같고 총 행 수도 같아야 한다. receipt와 로컬 commit 상태도 대조한다. 추가된 고아 주문·누락·ID 변조를 모두 잡는다.

## 프로세스 종료 구분

S03의 `am kill` 변형은 백그라운드 전환으로 worker를 멈춘 뒤의 유휴 PENDING 복원 시험이다. 실제 PID 종료가 없으면 BLOCKED다. 일반 force-stop 재실행과 구분한다.

`force_stop_after_pos_commit` 변형은 POS commit 사건 이후 최초·재시도 ACK를 모두 보류한다. 외부 실행기는 종료 전 PENDING·영수증 없음·POS 1건·ACK 방출 0회를 확인하고, adb force-stop과 PID 소멸·새 PID를 관측한다. 재실행 후에도 같은 전제를 확인한 다음 ACK 장벽을 해제한다. 전제를 놓치면 BLOCKED이며 성공으로 세지 않는다. 서버 자체가 임의 셸 명령을 실행하는 기능은 넣지 않는다. 최종 같은 ID·최초 receipt·POS 전체 1건·로컬 확인을 검증한다. OS 저메모리 회수나 전원 차단과 같다고 표기하지 않는다.

유휴 S03은 접수 후와 재실행 후 각각 PENDING·영수증 없음·POS 0건·submit 시도 0회를 검사하고 전경 worker의 사용자 중지 상태를 관측한다. 플래그만 남아 있고 전송했으면 SENT_WHILE_PAUSED로 FAIL이다. S01은 관측 뒤 연결 복구와 명시적 재개를 함께 실행해 관측 지연으로 소모된 시도 예산을 다시 시작한다.

C01 실기기는 debug 전용 한도 축소/저장 실패 주입으로 재현하고 release 변형에서 제외한다. C04는 사용자 중지가 프로세스 재실행에도 유지되는지 확인한다.

DB close/open은 저장소 재개 테스트다. 프로세스 종료 증거가 아니다. 자세한 절차는 [Windows 실행 준비](WINDOWS.md)에 있다.

## 테스트 자체 검증

- **MUT01:** 재시도 시 새 ID를 발급하도록 만든 사본 → S02가 POS의 중복 주문을 검출해야 한다.
- **MUT02:** ACK 전에 로컬 완료를 기록하는 사본 → S01/C03이 누락을 검출해야 한다.
- **MUT03:** 사용자 일시 중지 검사를 제거한 사본 → S03_am_kill의 중지 상태 검사에서 전송 시도를 검출해야 한다. 중지 위반이 드러나면 프로세스 종료 전에도 FAIL이다.
- 정상 기준 커밋이 먼저 통과해야 한다. 결함 사본이 컴파일 실패·환경 장애로 실패한 것은 검출 성공이 아니다. 기대한 데이터 불변식 위반을 확인한다.
- 테스트가 결함의 존재를 직접 검사하거나 결함 모드 자체를 실패 이유로 삼지 않는다. 같은 결과 판정 코드를 쓴다. 결함 스위치는 배포 APK에 넣지 않는다.

## 결과 형식과 배포 조건

각 실행은 source_commit, scenario_id, execution_level, network_path(loopback/emulator/adb-reverse/lan-wifi), OS/기기, 시작·종료 시각, 실제 실행 명령, 주입 사건, 관측 결과, 판정, 로그/DB 증거 위치를 남긴다. 에뮬레이터·adb reverse 통과를 실제 LAN/Windows 방화벽 검증으로 세지 않는다.

하네스 v2는 시작·종료 시 깨끗한 checkout을 확인하고 pm path의 실제 설치 APK 바이트 해시를 빌드 산출물과 대조한다. 수정 중인 소스·다른 APK면 BLOCKED다. 이는 CI의 빌드 절차와 함께 사용하는 증거이며 해시 자체가 소스에서 APK를 재현 빌드했다는 증명은 아니다.

판정은 PASS / FAIL / BLOCKED / NOT_RUN. 종료 코드 0만으로 전체 통과를 결정하지 않는다. 필수 관측이나 필수 실행이 없으면 전체 성공이 될 수 없다. 재실행 통과가 이전 실패를 지우지 않는다.

M3의 CI는 명세 검사·핵심 JVM 테스트·POS 테스트에 의존하는 APK 작업으로 구성한다. 필수 job의 실패·취소·skip은 배포 후보 생성 조건을 만족하지 못한다. 실제 GitHub Actions 실행을 확인하기 전에는 CI가 검증됐다고 쓰지 않는다. 실기기 결과는 별도 증거이고 CI 통과가 대신하지 않는다.
